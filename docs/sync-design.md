# 在线订阅与服务端主导同步设计（v3.3 草案）

状态：延迟重试、合并定向 Resync 与 D 仍是未实现、未完成协议验收的设计草案，入口见 [design.md](design.md) §16。A、B 最小版与 C 已迁入当前契约，入口见 §3、§4.1／§4.2、§5；本文不再重复定义这些能力。草案预留编号不能用于当前服务。

## 1. 结论与范围

本稿汇集同步方案与客户端契约；固定版本源码证据、历史查询实验及其验证边界见 [同步研究](sync-research.md)。

A 与 B 最小版的当前契约见 §3／§4.1，不新增协议、配置键、包或依赖。C 与 A/B/D 无功能依赖，当前契约见 §5。D 与 B 的延迟重试队列只保留准入门槛与预留设计，门槛量到数据之前不实现。

| 部分 | 作用 | 解决的问题 | 协议改动 | 建议范围 |
| --- | --- | --- | --- | --- |
| A 发送端幂等重发 | 加速 | 提交后、Publish 前崩溃 | 无；客户端用原 client_msg_id 重试 | 当前契约，见 §3 |
| B 已知失败可见化 | 观测 | Bus 层已知丢弃、Redis PUBLISH 无接收者 | 无 | 当前契约，见 §4.1 |
| B 延迟重试与定向 Resync | 加速 | Publish 报错、接收节点丢弃与查询失败 | 无；复用现有 2004 `{reason}` | 暂缓，见 §4.3 |
| 客户端周期对账 | 兜底 | 一切落库后未到达的消息 | 无；现有 60 秒定时器 | 保留 |
| C 按需在线订阅 | 减负 | 聊天页与会话列表的在线状态轮询 | 当前协议见 [在线状态订阅](integration.md#online-status-subscriptions) | 独立于本稿消息同步草案，见 §5 |
| D 服务端差异校准 | 替代兜底 | 让客户端停定时器 | 新增 1005、2006，扩展 2004 | 暂缓，见 §6.1 |

不新增 schema、outbox、Redis 必选项、消息中间件或 SDK 协议兼容层。不改变 seq 分配、可见范围、消息落库 ACK 语义、离线推送触发规则与 A13。置顶、免打扰、业务会话资料的完整增量通知不纳入首批范围。

### 目标与承诺边界

**不承诺硬上限。** 客户端一轮对账不构成完整性证明：1001 按 `updated_at` 倒序翻页，并发更新会把会话移到已读游标之前（D 的差异校准会遇到同一问题），这一轮就可能整条漏扫，只能等下一轮；耗时也只有分位数，没有确定上界，减去 p95 剩下的仍是 5% 的尾部。恢复时间改用有条件的统计 SLO：

```
条件：依赖健康、客户端前台且 WS 已连接、负载在压测档位内
指标：静默漏推在 T 秒内恢复的比例 ≥ P
构成：定时器周期 + 1001 完整翻页 + 缺口补拉；单轮漏扫由下一轮周期覆盖
```

| 路径 | 典型恢复 | 性质 |
| --- | --- | --- |
| A；以及暂缓的 §4.3 重试 | 等待重试 + 正常推送 | 加速，不提供任何时限；B 最小版只观测 |
| 客户端定时器 | 等待下一轮对账 + 补拉 | 统计 SLO，单轮漏扫由后续周期覆盖 |

初值取 T = 60 秒，P 由实测确定，不预先承诺。验收必须包含翻页期间会话移动的场景（§8.4），否则测出来的 P 偏高。A、B 上线并测得残余后，产品可以决定放宽定时器周期，放宽多少就是残余漏洞的典型发现时间。依赖故障期间分别记录原始端到端耗时及依赖恢复后的恢复耗时，不把故障期间伪装为成功。

## 2. 丢推来源与覆盖矩阵

Bus 每次 Publish 是 at-most-once，没有后台自动重试；客户端再次 Send 可触发 A 的幂等重发布（design §5.7）。下表列出已识别的落库后漏推路径。「可检测」指某个节点在失败发生时就知道；兜底统一是客户端周期对账，表中只写加速路径。

| 丢失点 | 可检测 | 现状 | 加速路径 |
| --- | --- | --- | --- |
| 发送节点提交后、Publish 前崩溃 | 否 | 无 ACK，客户端再次 Send 可按额度重发布并拿原 ACK | A；没有客户端重试时仍靠周期对账 |
| Redis PUBLISH 返回接收者数为 0 | 是 | B：计数并返回 `ErrBusFailed`，无自动重试 | 无；B 只观测 |
| `bus/local` 订阅通道满（`Publish` 的 `default` 分支） | 是 | B：逐个计丢弃、继续其他订阅，最终返回 `ErrBusFailed` | 无；B 只观测 |
| 发送节点 Publish 报错 | 是 | 只记日志，ACK 照常返回 | §4.3（暂缓）：延迟队列重试后合并定向 2004 |
| 接收节点分片队列满（`enqueuePush` 的 `default` 分支） | 是 | 丢弃并计数 | §4.3（暂缓）：直接合并定向 2004，不重试 |
| 接收节点 `ResolvePush` / `Recipients` / `VisibleTo` 失败 | 是 | 只记日志 | §4.3（暂缓）：重试一次后合并定向 2004 |
| 出站字节预算超限 | 是 | 已发 2004 | 不变 |
| 连接 send 队列满、写失败 | 是 | 关闭连接 | 不变；客户端重连后 1001 |
| Bus 订阅断开期间的事件 | 是（重连时） | 重连后 `ResyncAll` | 不变 |
| PG NOTIFY 在监听连接正常时丢失 | 否 | 无 | 无 |
| `group_changed` 丢失且消息落在 10 秒缓存窗口内 | 否 | 该成员收不到推送 | 无 |
| 发送端客户端在重试前消失 | 否 | 等下一次同步触发 | 无 |
| 客户端收到 2001/2004 但未处理 | 否（客户端缺陷） | 等下一次同步触发 | 无；重连或回前台同步覆盖 |

WS 提供连接内有序传输，但写出成功不证明客户端应用已处理。当前不为推送增加业务 ACK；断线靠重连同步，连接仍在但应用未处理的情况靠周期对账覆盖。

## 4. B：已知失败的可见化与定向 Resync

### 4.1 当前最小版本：Bus 层的已知丢失

B 最小版的 local 部分丢弃、Redis 零接收者与 PG 不变边界统一见 [design.md §6.1](design.md#61-bus--节点间事件广播)。它只暴露已知失败，不提供自动重试或定向 Resync；计数用于 §4.3 的准入评估。

### 4.2 计数的出口

当前实例计数、`app` 汇总和 `server.Stats()` 出口见 [design.md §6.1](design.md#61-bus--节点间事件广播)及 [宿主说明](embedding.md#启动与退出)。读取方法与返回字段以源码为准，没有 exporter 或 `/metrics`。这些信号不能直接表示消息漏推率；后续评估须先确认异常与消息漏推相关。后文的 `push_retry_*`、`push_publish_lost_total` 与 Resync 指标属于未实现候选设计，不能当作已有监控引用。

### 4.3 暂缓：延迟重试队列与合并定向 Resync

**准入：** A 与 §4.1 独立上线、观察一个完整周期后，重新发布、local 丢弃或 Redis 零接收者计数至少一项持续非零，再评估本节；都接近 0 时继续依赖客户端对账。现有 `service/message` 在包内记录并吞掉 Publish 错误，必须先设计显式失败回调或传递给补偿调度方的结果，不能只改 gateway，也不能让已提交消息的 ACK 因此变为失败。

以下为候选方案，参数尚未经故障注入验证，不代表现有默认值：

| 来源 | 候选处理 | 耗尽或过载后 |
| --- | --- | --- |
| Publish 失败 | 最多重试 3 次，延迟候选为 1s / 5s / 20s，绝对期限为首次失败后 30s | 计数 `push_publish_lost_total`；本地候选合并 Resync，跨节点仍由客户端定时器补齐 |
| ResolvePush / Recipients / VisibleTo 查询失败 | 最多重试 1 次，延迟 1s，共用首次失败后 30s 的期限；按 Ref 回读正文 | 本地候选合并 Resync |
| 分片队列满 | 不重试，避免扩大过载 | 直接合并 Resync |

调度必须满足：

- 每节点使用按到期时间排序的有界队列，候选容量 4096；任务只持消息引用和 `kind/attempt/dueAt/deadline`，不保留正文、不增加 Bus wire 字段。
- attempt 与绝对 deadline 贯穿实际执行和重新入分片队列，不能把任务退化为裸 payload。现有 `deliverOne` 每次新建 10s context，直接复用会无限安排“一次重试”；每次 I/O 必须取剩余期限与原操作超时的较小值，到期不再调用。dueAt 只是最早执行时间，不承诺精确调度。
- 定时 worker 只转交任务：Publish 候选为 4 个有界执行位，deliver 回原分片队列；目标已满按耗尽处理，不阻塞。队列满、Gateway seal 或 context 取消均非阻塞拒收并计数，不能接收 Shutdown 期间迟到提交而留下无人消费的任务。
- 退出时丢弃队列，客户端重连补齐。重试可能乱序到达，继续按连续 `local_max` 补缺口及去重，不引入服务端保序承诺。

Resync 候选为单聊 sender/recv 的本地连接（排除当前 sender_conn_id），或群缓存成员与本地在线用户的交集；缓存缺失视为未知。未知时允许全节点 pending，候选最小间隔 30s。候选不是授权结果，**帧只能携带 `{reason}`，不能泄露 conversation_id**；客户端仍走现有 1001＋按需 1002。

每连接一个 pending 标记合并重复触发，候选写出延迟为 5s 加 0–5s 抖动，节点每秒最多 200 帧，超额顺延。20,000 连接全部 pending 约需 100s，这只是该限速参数的算术结果，不是恢复时限。2004 保留字节预算豁免，仍受有界 send 队列限制；入队失败关闭连接。现有 Bus 重连 `ResyncAll` 继续立即写出。

通过 §4.2 的出口观测重试、耗尽、拒收和定向／全节点 Resync 次数，并记录 `resync_pending_age_seconds`；其中 `push_retry_exhausted_total` 与 `push_publish_lost_total` 供 D 的准入评估使用。正式实现前必须验证：

| 场景 | 必须断言 |
| --- | --- |
| Publish 重试耗尽、接收节点订阅正常 | 次数与绝对期限生效；跨节点由真实客户端定时器补齐，耗时计入 SLO，不能记为加速成功 |
| 分片满或查询失败 | 分片满不重试，查询只重试一次；Resync 合并／节流生效；候选用户拿不到未授权会话标识 |
| Resync 无法入队 | 关闭连接并在重连后补齐 |
| 反复失败或关停期间提交 | 不出现无限“一次重试”；拒收被计数，无残留任务；调度遵守 §8.1 的锁与退出约束 |

## 6. D：服务端差异校准与覆盖租约（暂缓）

### 6.1 准入门槛与周期成本

D 只在 A、B、C 上线后仍有可测残余丢失、且产品要求停客户端定时器时实现。判断依据：

- iOS 上报 `timer_discovered_gap`：定时器的 1001 拿到权威 `max_seq` 后，与**查询发起前**的已知目标比较，`max_seq > known_target` 计一次。

```
known_target = max(local_max, 该会话已有补拉任务的目标, 已收到推送的最大 seq)
```

  比较目标，不判断「有没有在途任务」。`local_max=10`、正在补到 15 时丢掉 `seq=16`，定时器仍是第一个发现 16 的人；按「有任务就排除」会漏算，任务被延长到 16 之后也不会再计数，指标恒为 0。同会话近期收到过更早的消息同样不能作为排除条件。
- 服务端 `push_retry_exhausted_total`、`push_publish_lost_total`。

健康时段上述数值持续接近 0，则不实现 D，改为与产品协商放宽定时器。否则先比较两种形态，再选周期：

| 形态 | 状态 | 出站 | 覆盖「客户端收到未处理」 |
| --- | --- | --- | --- |
| 差异提示 | 每用户上次观察 + 每连接基线 | 只发变化 | 否：水位不再变化就不再提示 |
| 周期推完整水位 | 无差异基线 | 每周期向连接发送完整水位，带宽随会话数与连接数增长 | 后续完整帧提供再次处理机会 |

周期推完整水位是把客户端 1001 变成服务端推，查询量不降，收益只有多端去重与去掉客户端调度；状态与恢复逻辑最少。两种形态都需要有界的数据库观察：单次查询限行数、限超时，超时按失败计并降级，不做无界扫描。

成本评估以实测完整一轮为单位：N 个有效用户、周期 Δ 时约有 N/Δ 轮观察每秒，每轮可能需要多页查询；完整水位出站还受同用户多连接放大。周期由 60s 缩到 20s 会使同条件观察频率变为 3 倍，但不能据此预测恢复延迟。批量化也不保证更快，负结果见 [查询成本实验](sync-research.md#9-查询成本实验)。

### 6.2 候选租约约束（随 D 暂缓）

租约为校准周期的 3 倍；过期恢复旧兜底，不自动重新协商，Ping/Pong 不续租。无需客户端同步 ACK。此处同步 ACK 不指发送消息的落库 ACK；D 的完整协议及验收仍待门槛通过后确定。

## 7. iOS 行为契约

本节是待客户端实现核对的交接要求，尚未取得 iOS 源码或设备；现有协议以 [Client synchronization](integration.md#client-synchronization) 为准。用户描述的 60 秒同步与 15 秒凭证检查不是服务端协议常量。

1. **发送重试。** 必需行为已归入 [接入协议](integration.md#websocket)：未收到 ACK 时保留原 client_msg_id 退避重试，直到 ACK 或用户取消；重连积压限量重发。客户端待验证的参数候选仍为 2s / 4s / 8s / 16s / 32s，之后连接期间每 60 秒一次；重连最多立即重发 20 条、最早未确认优先，其余保留退避计划。这些客户端候选值不是服务端协议常量。
2. **补拉调度。** 连续基线、权威可见范围、重入群／重置和分页规则遵守现行协议。同会话串行、跨会话并发有界，目标增长时合并任务，不并发拉重叠范围；失败保留任务并退避，不越过缺口。403 或成员范围变化时重新取权威范围再补拉或重建／删除基线；合法空区间与读取失败必须区分。同步进度不等于已读，已读只走 MarkRead。
3. **消息与 Resync。** 2001 只更新对应会话目标，不默认触发全量同步或完整列表刷新；当前 reason-only 2004 走 1001＋按需 1002。D 暂缓候选才会扩展 2004：items 逐条合并目标，full 触发 1001；现有服务不支持。2001/2004 无需客户端同步 ACK。
4. **周期对账。** 连接建立、回前台、Resync、定时器共用同步入口，同连接不并行跑两轮；运行中仍记录后续需求，不能丢触发或被其他会话的推送无限延后。翻页移动导致的单轮漏扫由后续周期覆盖。只有 D 已实现、协商成功、首次同步完成且租约有效时才可停定时器；过期恢复节奏待 §9 决策。D 仍保留初始化、重连／回前台同步和已知失败重试。
5. **在线订阅（C）。** 已归入 [当前接入协议](integration.md#online-status-subscriptions)，包括 UI 集合管理、请求失败重试、连接代次、快照替换与独立新鲜度期限；不在本文另设客户端契约。

A13 保持不变：同步基线不代表消息正文已持久化，App 重启或页面缓存丢失后仍须按页面需求恢复历史。业务元数据独立刷新：列表进入／恢复可见、本机操作后更新；消息和已读事件可更新内存，缺资料时合并请求。置顶、免打扰、群资料等跨端变化尚无完整通知覆盖，仍需校准，不能由消息水位推导业务列表也无需周期请求。

凭证检查仅在需要时刷新，鉴权依赖失败不视为凭证失效。后台停止定时同步与 UI 订阅并断 WS；普通断线退避重连，2002 不自动重连。每次连接使用独立 generation，丢弃旧响应及迟到续租；混合节点或回滚后重新判断能力，旧连接通知不能激活新连接的增强能力。

## 8. 落地与验收

### 8.1 配置与常量

A + B 最小版本的配置与实例计数边界见当前设计契约。§4.3 的候选参数只在该节维护，通过门槛后先作为包内常量验证，有实际环境调参需求才提升为配置。

D 的配置在门槛通过、对应代码实现时再定，不向当前 YAML 加入未被读取的字段。新增配置必须同步 `internal/config`、示例及全部部署配置并通过 drift test。C 的边界与常量来源见 [design.md §7.4](design.md#74-在线状态订阅)。

所有新请求沿用现有帧大小、帧速率与在途数限制；reason-only 2004 保留控制帧字节豁免，仍受 send 队列限制。重试与调度纳入 Gateway 工作跟踪和 Shutdown 期限，不新增每消息或每用户常驻 goroutine；锁内只更新内存，不持有 UserMap 锁做网络查询。日志不记录凭据或正文。

### 8.4 必须通过的验收

本节列 A + B 最小版本及配套客户端契约验收。§4.3 的验收在该节内。C 按 §5 引用的当前契约验证，包含过期读取、事件合并、快照顺序、预算丢弃、拒绝后重提交、连接清理与旧节点回落；不得把单元测试当作客户端联调或部署验收。D 的验收在 §6.1 门槛通过后补。

| 场景 | 必须断言 |
| --- | --- |
| 提交后、Publish 前终止发送进程，发送端客户端按契约重试 | 接收端不断线、无客户端周期查询，靠重新发布收到 2001；记录端到端恢复时间 |
| 快路径限流不通过 | 仍返回原 ACK，只跳过重新发布；事务内 duplicate 分支不重复扣额度 |
| `bus/local` 订阅通道满 | 每个满队列计一次，其他订阅仍可收到，最终返回 `errcode.ErrBusFailed`；不引入阻塞或重投 |
| Redis PUBLISH 返回接收者数 0 | 按 Publish 失败处理并计数；返回 ≥1 不作任何额外断言 |
| 1001 翻页期间会话被并发更新移动 | 记录漏扫发生率，并验证下一轮定时器补齐；该场景计入 §1 的 SLO 样本，不得从统计中剔除 |
| 同步中再次触发、补拉目标增长 | 后续需求不丢；同会话无重叠拉取、跨会话并发有界；失败不越过缺口 |
| 完整分页、相同时间戳、退群/重入、合法空区间与读取失败 | 按权威可见边界处理，不因空响应或失败误推进基线；重复 2001/2004 不重复计未读 |
| 仅持有 local_max 的 App 重启或页面缓存丢失 | 聊天页可见正文仍能恢复；元数据跨端校准不依赖消息水位变化 |

按专属一次性实例运行真实依赖测试，保持 `-p=1`；分别验证两类 Store 与各 Bus 支持组合。SLO 的测试必须让客户端定时器按产品周期真实运行并统计比例，加速路径的测试必须让定时器真正关闭，不能由测试脚本偷偷拉消息制造通过。

A/B 的三类计数分别验证尝试次数、逐订阅丢弃次数与零接收者次数，出口见 §4.2。暂未实现的新指标不伪装为已有监控。

## 9. 尚需验证的事项

**协议待决：D 租约过期后的恢复节奏。** 候选为立即恢复旧兜底，或延迟 0–10 秒随机恢复一次同步与旧兜底；现有两稿约定冲突。D 实现前须统一，不能丢掉原有的降级分散要求。

以下不是已通过的结论：A 的重新发布对发送端多设备的重复影响；Redis PUBLISH 接收者数在 go-redis 与集群模式下的可用性；§4.3 的延迟队列在真实故障注入下的耗尽率与 pending 年龄分布；C 的订阅引用内存、整集重读的读放大与完整快照出站带宽；D 的有界观察成本、建议限额能覆盖的生产规模。

尚未取得 `IMChatView.swift`、`IMStore.swift`、iOS 设备和业务 `/api/v1/im/conversations` 实现；§7 是交接契约，不是已证实的客户端缺陷。实际生命周期、旧 App 兼容、业务列表字段/刷新范围/查询成本及新协议端到端恢复均未验证。现有测试不能替代新协议或设备验收，范围见 [同步研究 §8](sync-research.md#8-nexo-现有测试与兼容边界)。

[历史查询实验](sync-research.md#9-查询成本实验) 保留原始批量 SQL 与修正对照的负结果，D 的观察不是「批量查询已验证更快」。实现阶段发现门槛不满足时保持 legacy 并回到设计，不通过静默截断、无限放宽时限或减少授权校验获得通过。
